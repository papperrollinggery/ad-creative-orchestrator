# ADCO 深度优化与验证记录

日期：2026-09-05。范围：本仓库源码、Skill 草稿、模板、测试和安装包镜像。

本文保留发布前优化阶段的验证快照；后续全局安装与公开发布由 v0.3.3 的 GitHub Release 及其安装包验证承接。

本次优化把 ADCO 的注意力进一步收回到实际广告成果，同时修复重复接入、旧分析污染与创意简报失效未提示的问题。源码检查、独立代码复审、合成创作试用与隔离安装验证均已完成。未修改全局安装或真实客户项目。

## 它要帮用户完成什么

ADCO 是由当前主模型执行的广告工作助手，负责把真实项目材料推进为用户要求的成果。CLI 提供证据登记、校验和版本衔接；创意推理来自当前主模型或用户明确选择的专业执行者。图片、视频与文件成品需要调用实际可用的制作工具。

| 用户的工作 | 应当交付的成果 | 关键质量判断 |
|---|---|---|
| 读 brief、会议纪要、参考资料 | 本轮目标、可用证据、矛盾与真正缺口 | 实际查看材料，不能只凭元数据理解图片或视频 |
| 做策略与创意 | 有产品依据的主张、具体机制、必要的备选与推荐理由 | 受众阻力、产品作用和可见结果连得起来，备选有实质差异 |
| 写脚本、导演阐述与分镜 | 可读、可表演、可继续制作的完整文本 | 因果、场地、人物、产品露出、声音与时长成立 |
| 做视觉方案或生成素材 | 对应任务的真实素材及采用判断 | 画面内容、资产真值、品牌角色与渠道用途成立 |
| 做提案、PPT和客户包 | 完整提案内容与经过验证的指定格式产物 | 内容先完成，版本、衍生文件、素材与审阅证据对应 |
| 吸收反馈、继续生产 | 保留已采用成果的定向修改 | 最新要求生效，修改范围明确，旧结论不会混入当前版本 |

一次性内部内容直接交付；持续管理项目时才登记状态；跨到客户可见版本、授权或发送准备时，再加载对应交付约束。已授权的多阶段工作继续做到请求终点，不以 intake、工作看板或 Gate 代替成品。

## 历史问题与本轮修复

早期青岭、Moncler 和 ThreadOps 案例证明过文件流程与结构校验，未证明真实创意、生成图像或客户效果。ThreadOps 试用还发生过将“缺 logo、缺产品图”等缺口当作创意输入的问题。后来的 Content Surface 已取消默认 Council、Dashboard 和交付账本；这些旧问题没有被重复报成仍未解决。

本次查到并修复的当前问题如下。

| 当前问题 | 实际修改 | 验证 |
|---|---|---|
| 新资料容易触发无谓项目初始化；普通创作读到长交付协议 | 明确一次性与持续管理边界，新增按需读取的 `creative_work.md`，把持久候选协议留在 `creative_contract.md` | 新上下文试用仅读取 Skill、创作参考与 brief，没有创建项目控制目录 |
| 生成请求写死旧模型，并只提供证据 ID 等结构信息 | 改为沿用当前主模型/明确选择；给出绑定字节摘要的原始证据入口 | 请求中可定位并验证实际证据文本，没有伪造实际模型回执 |
| “需要：2条”“三个机制不同的方向”等自然表达丢失数量 | 修复数量提取；大于六条时明确区分直接探索与持久导入容量 | 请求数量落实到候选 schema；冲突或超容量不静默改成默认数量 |
| 同一未改资料反复登记、解析，证据引用膨胀 | 文件/目录内容指纹与成功解析预算一致时复用；变更或失败可重试 | 同一来源两次运行由两个 SRC 变成一个，第二次解析文件数为零 |
| 同源修改后，旧事实与需求残留 | 去除已失去证据的派生事实和未确认需求；旧确认保留并标记需重新核对 | 同路径内容替换、确认失效回归通过 |
| 导出的旧模型分析仍能写回新资料状态 | 模型响应必须回传 `evidence_snapshot_sha256`，导入前精确校验 | 缺失/旧摘要均拒绝，原 facts/gaps 字节不变 |
| 上游变更后已有 creative brief 仍被增量检查报为 PASS | 增量校验复用导入/审阅的完整 manifest 与当前输入验证器 | 旧 brief 报 CHECK，重建后恢复；不改写旧创意或启动全量交付流程 |
| 已关闭问题重新出现在当前追问 | 摘要只纳入未关闭问题；已有明确目标时直接提示完成该目标 | 关闭缺口、明确目标但未命中提取关键词的回归通过 |

独立代码复审额外发现两项并已复测关闭：历史同路径多 SRC 在任何新登记写入前明确报 CHECK；混合批次逐个来源记录成功，某项失败不会迫使其他成功素材反复解析。文件夹中任一成员失败，整个文件夹来源继续保持可重试状态。解析前后内容指纹不一致时不写成功标记。

历史同路径多 SRC 采用保留原状态并阻断的处理方式，尚未自动迁移或合并。它需要明确的来源历史核对，不能把这次修复称为已经清理了旧客户项目。

## 创意质量是如何检验的

合成 brief 要求完成轻合便携桌灯的两个方向、推荐方向的完整 20 秒脚本、小红书三屏图文和电商首屏。固定一个演员、客厅同一张桌子，并限制事实、道具和产品宣称。

第一轮实际产物虽然结构完整，两方向却都是“犹豫—取灯—展开—写字”的不同讲法；片尾旁白也过密。补充检查后，第二轮时长与执行已改善，但独立内容审阅仍发现机制近似以及一张图混合两个动作时刻的问题。按原 brief 定向返修后，审阅确认：

- 方向一通过“让出一小块桌面”推动开始；方向二通过“使用后可收回的完整过程”推动开始，观看收益已不同。
- 推荐脚本仍满足 20 秒、单人、单桌、实体产品可见及宣称限制。
- 小红书第二屏明确为双动作拼贴；电商首屏展示形态与动作，渠道适配具有实质内容。
- 明确同类折叠灯也可能完成相近动作，没有把品类能力包装成品牌独有事实。

据此，创作参考补入了去掉标题/语气后比较起因、转折、结果，核对最近功能替代品，按实际表演时长检查口播，以及在机制重复难以自查时用一次只读复核并落实修改的办法。复核留在内部内容工作范围，不追加交付账本。

这是“产出—审阅—定向返修”的实际验证，不是首稿质量保证。没有执行图像/视频生成、PPT 渲染、客户审批或投放效果验证。

公开副本已将本机用户名、工作区与临时运行目录替换为占位符，创意内容和实测数值未改。原始摘要与脱敏说明见[公开副本说明](deep_optimization_20260905/public-normalization.json)。

## 效率实测

基线为本次修改前的 Git HEAD `1f5a773`；同一台机器、Python 3.13.13、同一份 145,028 字符合成文本，各做五次独立项目的首次/重复运行。下表为中位数。解析字符计数可能包含分块重叠，表中使用处理文件数和实际证据条目数。

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 首次命令耗时，包含进程启动 | 332.85 ms | 332.87 ms |
| 重复命令耗时，包含进程启动 | 350.13 ms | 264.93 ms |
| 重复运行内部阶段计时 | 87 ms | 8 ms |
| 第二次解析文件数 | 1 | 0 |
| 两次运行后的来源数量 | 2 | 1 |
| 两次运行后的证据条目 | 106 | 53 |
| 默认 Dashboard / 全量校验调用 | 0 / 0 | 0 / 0 |

重复命令耗时降低约 24.3%。这只说明该本地重复接入场景的表现，不代表所有任务的速度或模型额度变化。字节哈希仍要读取材料；首次处理没有测得改善。

普通创作原来加载的 `creative_contract.md` 为 11,345 字节，现在对应的 `creative_work.md` 为 4,103 字节，读取量减少约 64%。主入口仍为 119 行。协议没有被丢弃，它移到真正需要的持久交换路径。

原始测量：[基线](deep_optimization_20260905/performance-baseline.json)、[当前候选](deep_optimization_20260905/performance-candidate.json)。
